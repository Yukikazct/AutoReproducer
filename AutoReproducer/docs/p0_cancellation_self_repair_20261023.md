# 2026-10-23 紧急问题修复与验证

本轮优先处理 #59「任务卡死后无法重置」和 #61「复现失败后无法自行尝试修复」。用户提供的具体场景是下载依赖卡住，无法中断。

## 停止下载、安装与执行

网页增加“停止任务”。每个真实后台任务拥有独立 worker、取消令牌和进程所有权记录。点击停止后先发出一次中断，让安装器、作者运行和环境清理正常退出；独立 worker 五秒仍未响应时，Windows 通过本任务的 Job 回收进程树。运行环境准备期间的网络读取按块检查取消，等待受网络超时约束。

清理完成前保留运行状态并禁止重置；刷新页面不会丢失停止请求。安装进度写入取消终态，日志、报告和原始失败记录保留。清理失败或进程回收未确认时，保留错误凭据并阻止同运行环境继续启动任务，不把取消作为依赖安装失败再次切换镜像或尝试源码修复。

升级前启动且没有所有权记录的旧任务不能通过猜测 PID 强杀，需要先安全停止原服务。POSIX 的强制 worker 终止不能证明内层独立进程组全部结束，因此保守记录回收未确认，不自动清理仍可能被使用的环境。

## 有界自动修复与结果诊断

普通真实 PDF 网页默认开启兼容性源码修复，可手动关闭或切换严格核验。文件列表留空时，在原命令实际失败后，从最终 Python traceback 自动定位最多三个已冻结、哈希未变的源码文件；也可继续手动填写精确路径。标题、Mock、预设及直接服务调用的默认行为保持原有边界。

仅受支持的缺失属性或意外关键字参数进入源码兼容修复。候选在独立副本中经过 AST、文件保护与真实错误依据检查，最多两轮，重跑原命令；失败整体回滚。原源码、数据、命令和训练协议保持冻结。取消、超时、动态数据未冻结、Notebook 或不支持的异常保留明确原因，不宣称任意程序错误都能修好。详细规则见 [仓库兼容修复](repository_repairs.md)。

执行完成后，数值未满足既定参考规则或论文比较证据不足时，自动生成 `outcome_diagnosis.json` 和报告诊断章节。确定性观察、缺失证据与模型假设分别记录；模型假设必须引用本次证据 ID，最多调用一次。它不会修改模型、参数、数据划分、参考值、容差或重新训练。辅助诊断失败保留已完成的作者执行和原核验结论；修复后的结果使用批准副本的源码与哈希作为诊断依据。
